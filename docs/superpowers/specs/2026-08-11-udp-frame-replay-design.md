# 数据帧回放工具 — 设计文档

日期：2026-08-11
状态：已确认

## 1. 目标

跨平台桌面工具，从按行分割的十六进制数据文件中按帧提取数据，经 UDP 单播或组播发出。

数据文件的典型形态是每行一帧十六进制字符串，但行首常带有事件标识、序号、汉字标识等干扰内容，需要正确剔除。

核心能力：

- 按用户配置的手动规则剥离行首前缀，解码十六进制数据体
- UDP 单播与组播发送，可配置出站网卡、TTL、回环
- 节奏控制：发送间隔、循环开关与次数、起始行、结束行
- 按条件筛选行：前缀字段匹配 + 数据字节匹配
- 转发时修改字节：插入、替换、删除，以及长度、序号、时间戳、校验和等计算值
- 界面同时展示数据原文、实际发出的字节、发送日志

## 2. 约束

| 项 | 值 |
|---|---|
| 文件大小上限 | 1 GB |
| 典型行长 | 256 字节起步（1GB ≈ 400 万行） |
| 发送间隔精度 | 目标微秒级，毫秒可接受 |
| 目标平台 | Windows / Linux / macOS |

## 3. 非目标

- 不做接收/解析回包分析，本工具只负责发出
- 不做脚本引擎。修改能力止步于结构化规则 + 内置计算值
- 不做按原文时间戳回放（只支持固定间隔）
- 不支持 TCP、串口等其他传输方式

## 4. 技术选型

| 层 | 选择 | 理由 |
|---|---|---|
| 引擎 | Rust | 微秒级定时与零分配发送路径 |
| 外壳 | Tauri 2 | 体积小，Rust 后端原生 |
| 前端 | React 19 + TypeScript + Vite | 虚拟滚动生态成熟 |
| 虚拟滚动 | `@tanstack/react-virtual` | 400 万行必需 |
| 前端状态 | `zustand` | 配置树轻量可控 |

Rust 依赖：`memmap2`、`crossbeam-queue`、`socket2`、`crc`、`serde` / `serde_json`、`thiserror`。

### 5.1 帧数据准备策略

三种候选：

| 方案 | 做法 | 代价 |
|---|---|---|
| A 即时解析 | 发送线程逐帧现解析、现应用修改规则 | 内存最省，但每帧几百 ns~1μs 的解析开销挤占微秒级节拍预算，抖动直接暴露在定时上 |
| B 全量预处理 | 开始发送前把所有选中帧解析成字节数组 | 定时最准，但 1GB 文件可能吃掉 500MB+ 内存，且启动前有漫长卡顿 |
| **C 流水线预取** | 后台解析线程提前把未来 N 帧解析好、修改好填入有界环形缓冲；发送线程只做 `sendto` | 内存有界，发送线程零解析开销，定时与 B 等同 |

**选 C。** 决定性事实：hex 解析速度在 GB/s 量级，UDP 发送再快也就百万包/秒级，解析线程永远跑得比发送线程快，环形缓冲不会饿死。

### 5.2 线程模型

- **解析线程**：按「开始行 → 结束行」游标推进，逐行剥前缀 → hex 解码 → 筛选判定 → 应用修改规则 → 推入环形缓冲。不匹配筛选的行直接跳过，不占缓冲槽位。
- **发送线程**：绑定专用 OS 线程并提升优先级。毫秒模式用 `sleep_until`，高精度模式用「sleep 到目标前 1ms + 自旋」。只从缓冲取字节、`sendto`、记时间戳。**不做任何解析、不加锁、不分配内存。**
- **前端通信**：发送线程绝不直接发 event（微秒级下会淹死 IPC）。状态经无锁计数器聚合，控制层每 50ms 推一批给前端。

### 5.3 环形缓冲

8192 槽 × 2048 字节 ≈ 16MB。`crossbeam_queue::ArrayQueue` 承载槽位，发送线程用完把槽还回空闲队列，发送路径零堆分配。超过 2048 字节的帧走独立堆分配兜底路径（罕见，性能不敏感）。

### 5.4 行索引

`memmap2` 只读映射，首次打开单遍扫描建 `Vec<u32>` 行起始偏移（文件 ≤ 4GB）。400 万行约 16MB，1GB 文件构建耗时约 0.3 秒。按行号 O(1) 定位。

打开时记录文件 size + mtime，启动发送前复检——mmap 期间文件被外部截断会触发 SIGBUS。

## 6. 解析管线

### 6.1 前缀剥离（二选一模式）

**字段模式**：指定分隔符（空格 / 逗号 / Tab / 自定义，可勾选「连续空白算一个」），指定丢弃前 N 个字段，剩余字段全部拼接为数据体。

**偏移模式**：跳过前 N 个 **Unicode 字符**——按 char 计而非字节，否则汉字标识会被切碎。这是必须踩准的坑。

示例：`[TX] 000123 发送 01 A5 3F 2B` → 空格分隔 + 丢弃前 3 字段 → 数据体 `01 A5 3F 2B`。

### 6.2 Hex 解码

忽略所有空白与常见分隔符 `:` `-` `,`。遇到既非 hex 也非分隔符的字符即停止，其后内容忽略并记一条日志——这样天然容纳尾部注释，又不会静默吞掉真正的格式错误。奇数个 hex 字符判为错误行。

### 6.3 错误行策略

跳过 + 聚合计数 + 界面显示错误数，不中止发送。

## 7. 筛选规则

两类条件，多条 **AND** 组合，每条可单独取反：

- **前缀字段条件**：字段索引 + 等于/包含 + 值（字符串比较，支持汉字）
- **数据字节条件**：字节偏移 + 期望值 + 可选掩码，支持多字节序列

## 8. 修改规则引擎

### 8.1 决定一：结构性规则的偏移基于原始帧

规则之间互不影响——在 offset 5 插入 2 字节，不会导致另一条「offset 10 替换」的规则漂到 12。引擎收集全部编辑操作后按偏移**从后往前**一次性应用，因此不需要任何偏移重算。重叠区间会被检测出来并在界面标红。

### 8.2 决定二：两阶段执行

```
原始帧 ──阶段一(结构变更)──▶ 中间帧 ──阶段二(计算写回)──▶ 待发帧
        插入 / 删除 / 静态替换        长度 / 序号 / 时间戳 / 校验和
        偏移基于【原始帧】             偏移基于【中间帧】,按声明顺序执行
```

这正好解决「插入或删除字节后长度字段与校验和失效」的问题。

阶段二严格按用户在界面上排的顺序执行，因为**校验和必须最后算**（长度字段本身通常在校验范围内）。界面提供上移/下移，并在校验和规则不在末位时给出提示。

### 8.3 动态值类型

| 类型 | 参数 |
|---|---|
| 递增序号 | 起始值、步长、宽度、字节序、循环时是否重置 |
| 时间戳 | 宽度、单位（ms/μs）、绝对纪元或相对发送启动 |
| 帧长度 | 计算范围、宽度、字节序、是否含自身 |
| 校验和 | 算法、计算范围、宽度、字节序 |

校验和算法：sum8、sum16、xor8、CRC16-CCITT、CRC16-MODBUS、CRC16-XMODEM、CRC32。

范围的起止偏移**支持负数**表示从帧尾倒数——「第 2 字节到倒数第 2 字节」这种校验范围极常见。

### 8.4 条件生效

每条修改规则可绑定一个条件，直接复用第 7 节的筛选条件表达式，不另造语法。

### 8.5 性能

点击开始发送时全部规则**编译**成紧凑的 `Vec<CompiledOp>`。解析线程执行时无字符串解析、无哈希查找，输出写进可复用缓冲区，零分配。

### 8.6 边界

修改后帧长超过 UDP 上限 65507 字节 → 该帧记错误并跳过，不中止发送。

## 9. 网络层

- **单播**：目标 IP + 端口
- **组播**：组播地址 + 端口 + **出站网卡选择** + TTL + 是否回环
- **通用**：可选指定本地绑定地址 / 端口（有些接收端会校验源端口）

出站网卡选择在多网卡机器上是刚需，很多同类工具在这里翻车。

三块视图的分割条可拖动、可折叠。

### 10.1 实时预览

配置解析规则时，原文视图立刻用灰显/高亮标出「被丢弃的前缀」和「被采用的数据体」；改筛选规则时不匹配的行立刻变暗。后端 `preview(start, count)` 返回视口内每行的标注，纯计算，很快。

所见即所得，不用点发送才发现配错了。这是这个工具好不好用的分水岭。

### 10.2 高频发送时的诚实显示

每秒 10 万帧不可能逐帧渲染。后端维护「最近 1000 帧」环形快照，前端 20Hz 拉取。界面明确标注「采样显示 · 实际已发 N 帧」，不让用户误以为看到了全部。调试规则时用**单步模式**：点一次发一帧，完整可见。

### 10.3 日志聚合

同类错误按类型聚合计数（「第 3 类：奇数个 hex 字符 · 1,204 行 · 展开查看行号」），而不是每行一条。否则一个格式不对的文件会瞬间刷出几百万条日志把界面拖死。内存中保留上限 5 万条，环形淘汰。

### 10.4 Profile 持久化

整套配置（解析 + 筛选 + 修改 + 目标 + 节奏）存为 JSON，可保存 / 加载 / 切换。既然选了手动规则路线，配置复用就是刚需——换一种数据格式不该重配一遍。

## 11. 错误处理

### 11.1 预检优于运行时报错

点「开始发送」时先做一次完整校验，一次性列出所有问题并阻止启动：

- 规则编辑区间重叠
- 校验和范围超出帧长
- 组播地址不在 224.0.0.0/4
- 结束行小于开始行
- 绑定端口无权限
- 文件 size / mtime 与打开时不符

### 11.2 运行时错误分层

| 层 | 情况 | 处理 |
|---|---|---|
| 文件 | mmap 期间文件被外部截断（SIGBUS） | 启动发送前复检 size+mtime，变了就拒绝 |
| 解析 | 非法 hex / 奇数字符 / 空数据体 / 超长帧 | 跳过 + 聚合计数，不中止 |
| 网络 | `sendto` 返回 EWOULDBLOCK（内核发送缓冲满） | 退避重试 3 次后丢弃，状态栏**单列**「缓冲满丢弃 N 帧」 |
| 网络 | ICMP 端口不可达 → ECONNREFUSED | 记 warn 继续发（UDP 语义如此），界面提示「目标可能未监听」 |

「缓冲满丢弃」计数必须单独显示——否则用户会以为发了 10 万帧，实际内核吞掉一部分，而 UDP 不会告诉任何人。

## 12. 测试策略

- **解析器**：表驱动单测，覆盖各前缀形式、汉字边界、分隔符组合、每一类错误行
- **修改引擎**：重点验两阶段正确性——插入字节后长度字段与 CRC 是否正确。用标准测试向量钉死算法实现（CRC16-CCITT 对 `"123456789"` = `0x29B1`）
- **条件表达式**：掩码匹配、取反、多条 AND 组合
- **定时器**：绝不断言「精确 10μs」（必然 flaky）。发 1 万帧后断言 p99 误差 < 阈值，CI 上放宽
- **端到端**：本地起 UDP 接收 socket，发已知文件，逐字节断言收到内容。覆盖整条管线，性价比最高
- **大文件**：生成 1GB 合成文件，测索引构建耗时与内存，标记为 slow test

## 14. 已知取舍

- 微秒级是**软实时**。自旋期间占满一个 CPU 核心，操作系统调度仍会造成偶发几十微秒抖动，无法根除。界面显示真实抖动统计而非隐藏它。
- 1GB 文件 + 微秒间隔不会同时出现（那是几百 GB/s 数据率）。真实场景是「大文件慢速回放」或「小文件高频压测」二选一。引擎两者都支持，但不为该组合做额外优化。
- 10μs 间隔意味着 10 万包/秒，此时实际瓶颈是网卡和内核协议栈，不是定时器。
- 高频发送时发送视图只能采样显示，需要逐帧核对时用单步模式。

## 15. 决策记录

| # | 决策 | 备选 | 理由 |
|---|---|---|---|
| 1 | Rust + Tauri | Python+Qt / C#+Avalonia / Electron | 定时精度与体积 |
| 2 | 手动解析规则 | 自动启发式 / 正则 | 行为完全可预测 |

| 6 | 筛选多条 AND + 单条取反 | 两层 OR/AND 分组 | 覆盖实际场景且界面简单 |
| 7 | 无脚本引擎 | 内置 Rhai | 微秒级发送下脚本跑不动，复杂度不划算 |
